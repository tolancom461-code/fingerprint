# اختبار مسار استقبال البصمة المستقل

## الحالة قبل العمل

بوابة Railway منشورة بوضع `database-readonly` وتعرض بيانات TiDB المنسوخة. مدخلها لا يقبل ADMS ولا يشغل المعالجة أو التوصيل. وجود واجهة دخول وأعداد صحيحة لا يثبت نجاح استقبال جهاز جديد.

بتاريخ 9 نوفمبر 2026 أظهر فحص Windows للقراءة فقط أن `TolanBiometricService` تعمل، وأن الاتصال من `192.168.10.199` إلى `192.168.10.187:9095` قائم عبر TCP. لم تغير الخدمة أو إعدادات الجهاز. تعذرت استعلامات CIM المحلية، ونجحت بدائل القراءة `sc query` و`netstat` و`ipconfig` دون رفع الصلاحيات.

قرئت بيانات تعريف الجهاز من قاعدة `fingerprint` المنسوخة بحساب SELECT فقط: SpeedFace-V5L، والمنصة ZAM230_TFT، والبرنامج `ZAM230-NF50VA-1.1.9-OCM-4000-Ver1.0.1`. هذه بيانات لقطة المصدر وليست استعلامًا مباشرًا للجهاز أو إثباتًا حيًا لاتصاله بـRailway.

## حماية التاريخ وقناة الجهاز

أكد صاحب المشروع أن خيار USB أو تنزيل سجل الحضور غير ظاهر في قائمته. كما انتهى فحص TCP بسيط للمنفذ `4370` بمهلة دون اتصال؛ لم يرسل الفحص أي أمر للجهاز، ولا يعني انتهاء المهلة أن الجهاز لا يدعم أي وسيلة أخرى.

يوضح [دليل ZAM230 الرسمي](https://www.zkteco.me/download-file/3489)، في قسمي PC Connection وCloud Server Settings، وجود إعدادات TCP وHTTPS والنطاق وعنوان ADMS. ويذكر قسم Standalone Communication اتصال C/S لبرامج مثل ZKTime.Net وأن التفعيل يحتاج Comm Key وإعادة تشغيل. لم تغير هذه الإعدادات ولم تحمل أو تسجل DLL أو تثبت برنامجًا آخر. لم يجد الجرد المحدود DLL المعتادة zkemkeeper في System32/SysWOW64 أو تسجيل تثبيت باسم ZKTeco/ZKBio/ZKTime؛ لا يعد هذا بحثًا شاملًا في كل ملفات الجهاز.

لم يثبت توافق SDK قديم أو دوال تنزيل الحضور مع هذا الإصدار تحديدًا. لا ترسل أوامر DATA QUERY غير موثقة، ولا يعد فتح منفذ أو وجود سجل في القاعدة نسخة من كامل تاريخ الجهاز. طريقة الاستخراج تبقى معلقة حتى تحديد الطريقة المدعومة وحفظ ملف فعلي ومطابقة عدد حركاته وفترته وبصمته.

بحسب [أسئلة ZKTeco الرسمية](https://www.zkteco.com/en/faq.html)، قد يكون مفتاح HTTPS الخاص بـSpeedFace-V5L داخل Cloud Server Settings أو PC Connection. لا يكفي مكان المفتاح في الصور للحكم على سلوكه. ويفرض [Railway](https://docs.railway.com/networking/public-networking/specs-and-limits) TLS 1.2 أو أحدث وSNI؛ إعادة توجيه HTTP POST لا تصلح للاعتماد عليها لنقل جسم ATTLOG.

لم يثبت دعم إصدار الجهاز الحالي متطلبات الشهادة وSNI والتحقق المطلوبة للنشر المباشر. كما أن السماح بالرقم التسلسلي ليس مصادقة مستقلة. لذلك لم يضف وضع استقبال عام أو يغير نطاق الجهاز؛ يظل تحديد قناة موثقة ومحمية أو وسيط محلي مصادق خطوة مستقلة قبل اختبار الجهاز.

## مختبر الاستقبال

أضيف `scripts/verify-standalone-ingest-mysql.mjs` ليشغل مدخل `src/index.js` الحقيقي على MySQL محلي جديد ومنافذ loopback ومجلدات مملوكة للمختبر. لا يقبل اسم قاعدة قائمة أو سحابية، ولا المنافذ 9095/9096/9097، ولا يورث متغيرات TolanHR أو المصدر أو Bridge أو NODE_OPTIONS.

تعريفات الجداول العشرة في fixture حقيقية الأنواع والقيود والفهارس، مشتقة من metadata فقط؛ لا تستخدم صفوف الأشخاص أو الحركات أو النسخ الاحتياطية. تصنع أجهزة وأشخاص وروابط جديدة. يستعمل أحد الاختبارات هوية مصطنعة، وآخر يحاكي هوية ملف التطبيع الموجود داخل loopback فقط؛ لا يعد ذلك اتصالًا بالجهاز أو إثبات Firmware.

قبل الإصلاح نجحت تسع مجموعات فعلية: الإقلاع المعزول والتفاوض والتحقق من قائمة الأجهزة، وحفظ الحركات غير المعروفة دون تخمين دلالتها، وتطبيع ملف الجهاز المحاكى ومعالجته، وثبات الهوية عند إعادة الإرسال، ومنع الإقرار عند فشل الحفظ ثم التعافي، وإعادة تشغيل التطبيق وMySQL مع ثبات البيانات.

كشف الاختبار العاشر أن raw قديمًا مؤجلًا إلى retry ينشئ حدثًا نهائيًا تلقائيًا، بينما raw القديم المستحق عند الإقلاع لا ينشئه. لذلك كانت النتيجة الإجمالية قبل الإصلاح **فاشلة رغم نجاح مسار الاستقبال الأساسي**. حفظت النتيجة منفصلة في `verification/standalone-ingest-mysql-baseline-2026-11-09.json`، وأغلقت عمليات المختبر وحذف ملف تهيئة الأسرار.

## الإصلاح ونتائج ما بعده

أضيف قرار أهلية دائم في عمود اختياري مستقل `automatic_finalization_eligible` داخل جدول معالجة السجل. يحفظ مع raw في معاملته الأولى فقط، وبقيمة 1 إذا كان الحفظ جديدًا وصالحًا ومسموحًا والمعالجة التلقائية مفعلة وقت الحفظ. لا يرفع إعادة إرسال السجل القديم أهليته، ولا يؤخذ القرار من payload الجهاز أو ترتيب ID أو عمر التوقيت.

عند استرجاع سجل جديد مؤهل تحفظ نية المعالجة داخل معاملة canonical حتى لو كان التنفيذ التلقائي معطلًا مؤقتًا؛ تبقى النية قابلة للاستئناف عند إعادة التفعيل. السجل القديم المؤجل أو الموجود خارج دفعة الإقلاع لا ينشئ نية تلقائية. تغيير الأهلية لا يعيد إصدار الحدث أو يغير مفتاحه.

يفحص مدخل الكتابة العمود قبل الاستقبال إذا كانت المعالجة التلقائية مفعلة، ويرفض بدءها إن لم يجهز المخطط. عند التعطيل يبقى المخطط القديم صالحًا، وإن كان العمود موجودًا تقرأ أهلية السجلات السابقة وتحفظ بدل فقدها. بقي مخطط القراءة وقواعده متوافقين مع TiDB الحالية دون ترقية.

نجح **13/13 فحصًا فعليًا** على MySQL المحلي بعد الإصلاح، بما فيها الفحوص التسعة السابقة والضوابط التالية:

- القديم المستحق عند الإقلاع والقديم المؤجل إلى retry: canonical واحد لكل منهما، و0 حدث نهائي و0 intent تلقائي، قبل إعادة الإرسال وبعده.
- الجديد المؤهل المستحق عند إعادة التشغيل والجديد المؤهل المؤجل لأول معالجة بعدها: حدث نهائي واحد وهوية ثابتة عند إعادة الإرسال.
- التقاط الأهلية أثناء التشغيل، ثم إنشاء canonical أثناء تعطيل التلقائي، ثم إعادة التفعيل: حفظت النية دون تنفيذ أثناء التعطيل، ثم نتج حدث واحد دون تكرار.

نجحت اختبارات الحزمة **359/359**، وراجع التنفيذ وكيل مستقل دون ملاحظات مؤثرة. طابقت ملفات الأصل الـ109 وملفات TolanHR الـ454 المرجع دون تغيير. اجتاز فحص توزيع من 252 ملفًا، واستبعدت ملفات الاعتماد الخاصة السبعة والنسخ والتقارير وقيم الأسرار من Git والحزمة وDocker.

أغلقت عمليتا التطبيق وMySQL المملوكتان للمختبر، وأزيل ملف تهيئة الأسرار، وبقيت بيانات الاختبار المصطنعة محليًا للتحقق. أثبت الفحص اللاحق استمرار خدمة Windows القائمة واتصال الجهاز بها على 9095، واستمرار `/ready` في Railway بوضع database-readonly وحالة 200.

الأدلة المحلية المستبعدة: `verification/standalone-ingest-mysql-eligibility-verification.json`، و`standalone-ingest-mysql-eligibility.log`، و`standalone-ingest-eligibility-all-tests.log`، و`standalone-ingest-postchecks-2026-11-09.json`. يبقى دليل الفشل السابق محفوظًا للمقارنة.

## ما لم ينفذ والخطوة التالية

ملف [الترقية اليدوية للوجهة](../database/ADD_AUTOMATIC_FINALIZATION_ELIGIBILITY_FINGERPRINT_NOT_APPLIED.sql) أعد للمراجعة فقط، ولم ينفذ على `fingerprint` السحابية أو قاعدة `test`. لا تضعه في أمر بدء Railway؛ التفعيل اللاحق يحتاج نسخة وجهة احتياطية وتحققًا وترقية منفصلة. لم تتغير متغيرات Railway ولا يحتاج وضع القراءة الحالي تعديلًا.

الأهلية تعالج السجلات الموجودة قبل التفعيل مقابل الحفظ الجديد. **رفع تاريخ قديم من الجهاز لاحقًا أثناء التلقائي قد يصنف كحفظ جديد**؛ لذلك يظل استيراد التاريخ محتاجًا إلى عزل ومراجعة قبل التوصيل. لا يعد هذا الاختبار تنزيلًا للتاريخ أو تحويلًا تشغيليًا أو مصادقة لجهاز أو اختبار HTTPS/SNI/Firmware.

سئل صاحب المشروع عن حالة الخيار بالمسار الرسمي: **System → Security Settings → Standalone Communication**. المطلوب عرض حالته فقط لتحديد قناة استخراج السجلات بعد عدم ظهور USB؛ لا تفعيل أو إعادة تشغيل. شرح له أن الغرض سحب التاريخ إلى الكمبيوتر، لا تغيير اتصال البوابة. الحالة الفعلية للخيار غير معروفة بعد.

تبقى المرحلة الأولى مفتوحة لاختبار قناة الجهاز الفعلية واستقبال حركة منه وحفظها ومنع تكرارها بعد حماية التاريخ، وفق شروط الخطة الأصلية.

متابعة لاحقة: طبق عمود الأهلية على وجهة TiDB ضمن إجراء إعداد مصادق عليه بعد نسخة حديثة، وأعد مدخل استقبال سحابي وكاتب محدود وقوائم الحركات ومستخدمي الأجهزة. دليل [الاستقبال السحابي](CLOUD_INGEST_DEPLOYMENT_2026-11-09.md) هو المرجع الأحدث لحالة الترقية، ويحدث حالة «غير منفذ» التي تصف نهاية W019 أعلاه. لم يتغير اتصال الجهاز أو النشر العام ضمن التجهيز.
