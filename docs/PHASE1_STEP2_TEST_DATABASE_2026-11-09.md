# تشغيل البوابة من قاعدة اختبار معزولة

التاريخ: 9 نوفمبر 2026. الحالة: مكتملة برمجيًا ومختبرة فعليًا على MySQL محلي معزول. لم تفعل على Railway أو تتصل بقاعدة الإنتاج. سجل ما قبل التنفيذ وما بعده في خطة الفصل الرئيسية تحت العمل العاشر.

## نطاق التشغيل

أضيف مدخل `src/test-portal.js` مستقل لعرض بيانات قاعدة اختبار بصلاحية قراءة فقط. لا يستورد `src/index.js` ولا يشغل استقبال الأجهزة أو معالجة البصمات أو إعادة معالجة التاريخ أو موصل TolanHR أو الإدارة المحلية أو API البرامج الأخرى. لا ينشئ أو يعدل جداول عند الإقلاع.

إعداداته مستقلة عن `BIOMETRIC_DB_*` ومتغيرات demo. لا يقرأ ملف `.env` تلقائيًا. يبقى Dockerfile وأمر Railway الافتراضي على `src/railway-staging.js`؛ رفع هذه الملفات وحده لا يحول الخدمة المنشورة إلى قاعدة.

## الإعداد الصريح

مثال عام خالٍ من الأسرار في [.env.readonly-test.example](../.env.readonly-test.example). لإنشاء hash لحساب اختبار خاص استخدم الأداة الموجودة `npm run admin:password-hash` دون تمرير كلمة المرور ضمن الأمر.

| الإعداد | الغرض |
| --- | --- |
| `PORT` | منفذ البوابة؛ الافتراضي 8081 |
| `BIOMETRIC_READ_PORTAL_HOST` | الافتراضي loopback؛ يقبل `0.0.0.0` للنشر المعزول عند تجهيزه |
| `BIOMETRIC_READ_PORTAL_ORIGIN` | أصل HTTPS للبوابة، أو HTTP على loopback للاختبار |
| `BIOMETRIC_READ_PORTAL_ADMIN_USERNAME` و`BIOMETRIC_READ_PORTAL_ADMIN_PASSWORD_HASH` | حساب الدخول إلى بوابة الاختبار |
| `BIOMETRIC_READ_PORTAL_VIEWER_USERNAME` و`BIOMETRIC_READ_PORTAL_VIEWER_PASSWORD_HASH` | حساب عرض اختياري؛ يضبط الاسمان معًا |
| `BIOMETRIC_TEST_DB_HOST` و`BIOMETRIC_TEST_DB_PORT` و`BIOMETRIC_TEST_DB_USER` و`BIOMETRIC_TEST_DB_PASSWORD` | اتصال قاعدة الاختبار، دون fallback إلى الإنتاج |
| `BIOMETRIC_TEST_DB_NAME` | اسم مطابق لـ`biometric_portal_test_` مع لاحقة من حروف صغيرة وأرقام وشرطة سفلية |
| `BIOMETRIC_TEST_DB_CONFIRMED_NAME` | الاستثناء الوحيد للاسم `fingerprint` يتطلب القيمة الحرفية نفسها بعد تأكيد تخصيصه للتجربة؛ لا يسمح بأسماء أخرى |
| `BIOMETRIC_TEST_DB_INSTANCE_ID` | UUID v4 يطابق علامة هوية قاعدة الاختبار |
| `BIOMETRIC_TEST_DB_SSL_MODE` | `required` افتراضيًا؛ `disabled` متاح على loopback فقط |
| `BIOMETRIC_TEST_DB_CONNECT_TIMEOUT_MS` و`BIOMETRIC_TEST_DB_QUERY_TIMEOUT_MS` | مهل بين 100 و10000 ميلي ثانية |

تشغيل صريح بعد إعداد قاعدة الاختبار والحساب:

```powershell
node --env-file=.env.readonly-test src/test-portal.js
```

أو `npm run start:portal-test` إذا كانت القيم مضبوطة مسبقًا في بيئة العملية. لا تستخدم بيانات اعتماد الإنتاج في هذا المدخل.

## متطلبات القاعدة وحساب القراءة

يفحص الإقلاع اسم القاعدة، والمخطط الحالي لجداول `biometric_svc_*` العشرة وأعمدتها وفهارسها وترميزها، وجدول هوية اختبار مستقلًا. هذا الفحص SELECT فقط؛ ليس ترحيلًا أو أداة إنشاء مخطط إنتاج.

يحتوي جدول `biometric_portal_test_identity` صفًا واحدًا بالقيمتين `purpose = portal-isolated-test-v1` و`instance_id` المطابقة للإعداد. لا يكفي تسمية قاعدة إنتاج باسم `test`، ولا يقبل هذا الاسم أصلًا. بعد تأكيد صاحب المشروع تخصيص قاعدة سحابية فارغة باسم `fingerprint`، أضيف قبول هذا الاسم فقط عند تأكيده صراحةً بـ`BIOMETRIC_TEST_DB_CONFIRMED_NAME=fingerprint`، مع استمرار فحص هوية القاعدة والمنح والمخطط. لا يتيح متغير التأكيد استخدام أسماء أخرى.

حساب SQL مخصص بمنح SELECT صريحة لكل جدول من الجداول العشرة ولجدول الهوية فقط. يرفض الحارس منح SELECT العامة أو على كامل schema، وأي كتابة أو GRANT OPTION أو أدوار أو صيغ منح غير معروفة. يجب أن يعيد `CURRENT_ROLE()` القيمة `NONE`، ويستخدم الاستعلام الاسم المستعار `active_roles` لتوافق TiDB. يسهل هذا اختبار الحدود نفسها على MySQL وTiDB، دون التعامل مع أنماط wildcard في منح schema.

المصادر الرسمية: [منح المستخدم الحالي في TiDB](https://docs.pingcap.com/tidb/v7.5/sql-statement-show-grants/) و[تقييم منح الوصول في MySQL](https://dev.mysql.com/doc/refman/8.4/en/request-access.html). منع الكتابة يعتمد منح الحساب وواجهة القراءة الضيقة؛ لا يعتمد `SET TRANSACTION READ ONLY` الذي قد يعامل كوظيفة غير منفذة في [TiDB](https://docs.pingcap.com/tidb/stable/system-variables/).

تمنع واجهة القاعدة تمرير الكتابة والاستعلامات المركبة وعمليات القراءة ذات الآثار الجانبية. البحث يمرر بوسائط prepared. المهل تشمل انتظار الاتصال والاستعلام والإغلاق، والأخطاء العامة لا تكشف SQL أو قيم الاتصال أو المنح.

## فحص الحياة والجاهزية

- `GET /health`: بقاء عملية HTTP متاحة، ويعيد `OK`. لا يثبت صحة القاعدة.
- `GET /ready`: يتحقق من الاتصال واسم القاعدة والمنح والأدوار والهوية؛ يعيد 200 عند النجاح و503 عند التعثر، دون تفاصيل اتصال.
- إعادة اتصال بعد تعثر شبكة مسموحة. تغير الهوية أو المنح إلى حالة غير مقبولة يغلق مصدر القراءة، ويلزم تصحيح الإعداد وإعادة التشغيل.

لا يعلن أي من الفحصين اتصال جهاز البصمة أو تسليم حركات إلى برامج أخرى. تظل قراءة بيانات البوابة محمية بجلسة، وكتابة المدير والمشاهد مرفوضة في هذا الوضع.

## اختبار MySQL الفعلي محليًا

```powershell
npm run verify:portal-mysql
```

تستخدم الأداة MySQL المثبت في المسار الافتراضي على Windows، أو مسارًا صريحًا:

```powershell
node scripts/verify-test-portal-mysql.mjs --mysqld-path "C:\Program Files\MySQL\MySQL Server 8.4\bin\mysqld.exe"
```

الأداة لا تقبل قاعدة أو بيانات اعتماد أو datadir قائمًا. تنشئ مجلدًا جديدًا تحت `verification` وتختار منافذ loopback مؤقتة وتستخدم `--no-defaults`، دون تثبيت خدمة Windows. تضبط كلمات مرور عشوائية خاصة بالاختبار، وتحذف ملف تهيئة السر بعد بدء القاعدة، ولا تطبع كلمات المرور أو رموز الجلسة أو المنح.

تنشئ الجداول من عقد الأعمدة والفهارس لاختبار القراءة، وتضيف جهازًا وشخصًا وحركة مصطنعة. **هذا المخطط fixture للاختبار وليس مخطط ترحيل إنتاج**؛ لا يمثل تشغيل مسار استقبال أو معالجة البصمات.

يشمل الفحص منع INSERT من حساب القاعدة، ومنع إنشاء شخص عبر HTTP حتى للمدير، ومطابقة البيانات والمعرّفات والتوقيت بعد إعادة تشغيل البوابة وبعد توقف MySQL وإعادة تشغيله. توقف الأداة العمليات التي أنشأتها فقط، وتحتفظ بمجلد بيانات الاختبار ولا تحفظ كلمات مرور تشغيله في التقرير.

تكتب النتيجة المنقحة في `verification/phase1-step2-mysql-verification.json`، وهو مستبعد من Git والحزمة وصورة Docker. لا تشغل الأداة كأمر بدء Railway.

## النتائج والمتابعة

نجح الاختبار الفعلي في 9 نوفمبر 2026 على MySQL 8.4: **11/11 فحصًا**، من إنشاء قاعدة الاختبار ورفض الكتابة وقراءة البيانات عبر البوابة حتى تطابق السجلات بعد إعادة تشغيل التطبيق وMySQL نفسه. أثناء توقف القاعدة أعاد `/ready` الحالة 503 ثم تعافى إلى 200، مع بقاء فحص حياة HTTP متاحًا. حفظت معرّفات أكبر من الحد الآمن لـJavaScript وUUID وكسور UTC ذات الدقة الستية `.123456` دون تغيير.

نجحت اختبارات الحزمة **276/276**، ومنها 28 جديدة للإعدادات وحراسة القراءة ودورة التشغيل. فحصت حزمة توزيع من 221 ملفًا دون أسرار أو بيانات المختبر، وطابقت بصمات 109 ملفات من الخدمة الأصلية و454 ملفًا من TolanHR مرجعها السابق.

أوقفت عمليات المختبر وأزيل ملف الأسرار المؤقت، مع الاحتفاظ بمجلد البيانات المعزول. أوقف MySQL بأمر SHUTDOWN؛ إعادة تشغيل التطبيق اختبرت بإيقاف عملية الطفل على Windows، ولا تمثل إثبات إشارات الإيقاف داخل حاوية Linux. لا يتطلب إثبات بقاء هذه البيانات أي نقل أو نسخ من قاعدة الإنتاج.

الأدلة المحلية المستبعدة من التوزيع: `verification/phase1-step2-mysql-verification.json` و`verification/phase1-step2-tests.log` و`verification/phase1-step2-original-comparison.json` و`verification/phase1-step2-package.json`.

الاختبار المحلي لا يثبت نشر هذا المدخل أو توافق نسخة TiDB السحابية أو اختبار TLS البعيد أو استقبال جهاز. تفعيل قاعدة اختبار على Railway لاحقًا يحتاج قاعدة مخصصة وحساب القراءة وعلامة الهوية والمتغيرات وأمر البدء المحدد، ثم فحص الجاهزية والدخول على النطاق.
